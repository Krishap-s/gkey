# Design

## Components

- `gkey-service` is a system service running as the dedicated `gkey`
  account, the only one allowed to use the TPM (through the `tss`
  group) and `/dev/uhid`.  It creates a virtual USB HID device that web
  browsers recognise as a FIDO2 security key, implements the CTAPHID
  transport and the CTAP 2.0 commands on it, and acts for the user of
  the active session on the seat, as reported by systemd-logind: only
  that user can open the device.
- `gkey` is a command line tool with which users list and delete their
  own credentials.  It calls the service's interface on the system bus;
  the service identifies callers by the user ID the bus reports.
- A GTK4 key management tool is planned.

The CTAPHID engine (`src/ctaphid.rs`) and the D-Bus interface
(`src/manager.rs`) run on an asynchronous event loop.  CBOR and
management requests are handed to the authenticator (`src/ctap2.rs`),
which owns the TPM connection and runs on its own thread, so that
keepalive messages and cancellation keep working while the
authenticator waits for the TPM or for the user.

## Root of trust

All keys descend from a storage primary key (ECC P-256, restricted
decryption) that the TPM derives from the seed of its owner hierarchy
each time gkey connects.  Nothing is stored in TPM non-volatile memory.

- Each user has a user key: a restricted storage key created under the
  primary key with a random 256-bit password, generated by the TPM and
  readable only by the service.  The TPM refuses to load the objects
  below it without that password, so other programs able to use the
  TPM cannot use any user's credentials.
- Each credential is a P-256 signing key created by `TPM2_Create` under
  the user key, with `fixedTPM` and `fixedParent`.  Its wrapped private
  area is stored in the keystore and loaded only to sign.
- The keystore is encrypted with AES-256-GCM.  Its key comes from the
  TPM's random number generator and is sealed under the user key as a
  keyed hash object.
- Commands run in an HMAC session salted with the primary key, with
  command and response parameter encryption.
- The keystore records a digest of the primary public key, to report
  a cleared or different TPM clearly.

## Keystore

Each user has a single CBOR file, `/var/lib/gkey/UID/keystore`, holding
the user key and its password, the sealed key and the encrypted
credential list.  The state directory is private to the service, so
users can neither read nor replace keystores, which rules out rolling
them back.  Keystores are replaced atomically on every change, and
access is serialised with `flock` on `keystore.lock`.

Credential IDs are 16 random bytes.  Every credential, discoverable or
not, is kept in the keystore, so credentials can be listed and deleted.

## User consent

The service asks polkit to authorize the action
`io.github.krishap_s.gkey.use-passkey` for the oldest process of the user
in their logind session (polkit's rules engine aborts on session
subjects, so the session cannot be the subject itself).
The desktop's authentication agent shows the request and checks the
user's password through PAM, so fingerprint readers and other PAM
modules work, and the service never sees the password.  polkit has no
confirmation without authentication, so presence and verification
both require it.  The policy's owner annotation lets the `gkey` account
check authorizations for other users' subjects.  Deleting credentials
through D-Bus requires `io.github.krishap_s.gkey.manage`.
Alternatively an external command decides.
